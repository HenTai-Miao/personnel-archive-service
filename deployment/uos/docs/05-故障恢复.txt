人员档案数据服务——故障恢复
============================

一、服务没有启动

先执行启动脚本，它会在失败时自动输出有界诊断：

    sudo ./启动prod环境.sh

也可以按顺序检查，只收集状态和安全日志，不输出 JAR 内的固定配置值：

    systemctl status personnel-archive-service.service --no-pager
    journalctl -u personnel-archive-service.service -n 200 --no-pager
    tail -n 200 /data/personnel-archive-service/log/log.$(date +%F).log
    java -version
    ss -ltn | grep ':18080'
    systemctl status mysql --no-pager

若 18080 被其他进程占用，先确认进程归属，不要随意结束未知业务进程。安装器不会抢占
端口。

二、数据库认证或授权失败

1. 确认 MySQL 正常运行且监听 127.0.0.1:3306。
2. 以数据库管理员身份运行 mysql -u root -p。
3. 执行 mysql/01-确认应用账号授权.sql 并检查 SHOW GRANTS。
4. 确认应用账号密码仍与本次交付 JAR 的固定 prod 配置一致，不要显示或记录该值。
5. 重启服务并检查 database_connection、flyway_migration 和 service 事件。

不要用通配主机规避本机连接问题。若数据库密码已经改变，必须在开发机同步修改 prod
配置、重新测试并制作离线包；重复安装旧包不会自动修正密码。

三、Flyway 迁移失败

根据 flyway 阶段、异常类型和安全化调用位置确认原因，常见原因是权限不足、数据库不
是预期结构、旧表被人工修改或 MySQL 版本不兼容。修复真实原因后重启，Flyway 会依据
flyway_schema_history 继续。不要删除、伪造或手工改写迁移记录；最终 version 15 的
success 必须为 1。

四、JAR 更新后恢复

保留上一份已经校验通过的完整离线包。使用可信包重新运行 sudo ./install.sh，可替换
JAR 和 systemd 单元，同时保留全部 log 历史。安装前后核对
SHA256SUMS，不要从不明来源单独拿 JAR 覆盖生产文件。

三项安全值固定在 prod JAR 并与已有数据绑定：换成使用其他 HMAC/AES 值构建的 JAR 会
导致查询或解密失败，换 token pepper 会使现有会话失效。恢复时必须使用保存过的同一套
可信生产包，不能为已有数据库重新生成三项值。

五、日志磁盘空间

历史日志每天一份 `log.YYYY-MM-DD.log` 纯文本文件，不压缩、永久保留，应用不会自动删除。
定期执行：

    df -h /data
    du -sh /data/personnel-archive-service/log

空间不足前应扩容或把已验证的历史日志复制到公司受控归档介质；确认归档完整后再由授权
运维人员按公司制度处理源文件，不能让磁盘耗尽导致数据库或服务写入失败。

六、提交排障材料

优先提供发生时间、requestId、服务状态、固定结果码和已脱敏日志片段。发送前仍应人工
检查。绝不提供安全密钥配置、数据库导出、Excel 原件、照片、密码、令牌或密钥。
