# 中阿混合分隔日期兼容设计

## 背景与目标

当前 `SourceValueParserV1` 能识别 `二〇二四年五月三日` 和 `2024.5.3`，但不能识别
`二〇二四.五.三`：带年月日单位的规则允许中文数字，而分隔符规则只允许阿拉伯数字。
这会使本来语义明确的 Excel 日期在导入时被判为“日期格式不正确”。

本次扩展日期识别能力，同时保持既有档案不变量：

- 数据库、详情接口和导出 Excel 继续保留并使用来源原文；
- 年、月、日只作为额外数字投影，不替换原文，不补齐来源没有提供的精度；
- 不修改已经被 Flyway V10 使用的 `SourceValueParserV1`；
- MySQL 与 KingbaseES 使用相同的新解释规则和迁移结果。

## 支持边界

新增 `SourceValueParserV2`。单值日期先委托 V1 解析，V1 失败后才尝试新的分隔日期语法；
日期区间继续用 V1/V2 单值规则校验两端，但必须从原字符串切分，以免 V1 的识别副本
规范化全角符号或内部空格。已有输入的日期含义不变，来源文本逐字保留。

V2 新增支持的核心示例如下：

| 来源原文 | 精度 | 数字投影 |
|---|---|---|
| `二〇二四.五` | 年月 | 年 `2024`、月 `5`、日 `NULL` |
| `二〇二四.五.三` | 年月日 | 年 `2024`、月 `5`、日 `3` |
| `二〇二四/5/三` | 年月日 | 年 `2024`、月 `5`、日 `3` |
| `2024-五月` | 年月 | 年 `2024`、月 `5`、日 `NULL` |
| `二〇2四年.05月.三日` | 年月日 | 年 `2024`、月 `5`、日 `3` |
| `二〇二四．五．三` | 年月日 | 年 `2024`、月 `5`、日 `3` |

具体语法约束如下：

- 日期只支持“年”“年月”“年月日”三种现有精度。
- 分隔符支持半角或 NFKC 后等价的 `.`、`/`、`-`；同一日期内可以混用这些分隔符。
- 年、月、日三个片段可分别使用阿拉伯数字或中文计数数字，因此
  `二〇二四/5/三` 合法。
- 四位年份继续允许逐位的中阿数字混写，例如 `二〇2四`；月、日不接受
  `十5` 这类片段内部混写。
- 分隔形式中的年、月、日片段可分别保留正确的 `年`、`月`、`日` 后缀，
  因此 `2024-五月` 和 `二〇二四年.五月.三日` 合法。
- 不新增 `号`、英文月份、两位年份、模糊日期或自然语言猜测。
- 空白只用于识别时去除；Unicode 全角兼容只用于识别。返回和落库的原文保持读取层
  取得的字符串，不用规范化文本覆盖。

年份仍限制为 `1000..9999`。月份和日期必须通过 `YearMonth`、`LocalDate` 的真实日历
校验；例如 `二〇二四.十三.三`、`二〇二三.二.二十九` 继续失败。年-only 输入继续由
V1 处理，年月不补日，年不补月和日。

## 版本边界与模块职责

`SourceValueParserV1`、`StructuredSourceValueBackfillV1` 和 V10 迁移保持原样，继续表示
已经发布的历史解释合同。

`SourceValueParserV2` 对外提供与 V1 对齐的年龄、日期和日期区间入口：

- 年龄入口直接复用 V1，本次不增加或改变年龄语义；
- 日期入口先调用 V1，再解析新增的中阿混合分隔形式；
- 日期区间入口在原字符串上定位边界并使用 V2 单值入口校验两端，保留现有区间分隔符和
  “今/现在/至今”语义，也不直接返回 V1 基于规范化副本构造的端点文本。

日期区间先把整个文本尝试为单个日期，确保 `二〇二四-五-三` 不会被误拆成区间；只有
单日期解析失败时，才枚举 `-`、`—`、`–`、`~`、`至` 的候选切分点。只有唯一一个切分
能让两端都成为有效日期或合法当前标记时才生成区间投影；零个或多个候选都保持现有的
“不生成投影、原文仍保留”行为。切分判断使用规范化副本，但返回的起止文本直接截取
来源字符串，因此全角标点和内部空格也逐字保留。

Hutool 继续只负责中文计数数字转换。日期结构、四位年份逐位解释、来源精度和日历合法性
仍由项目代码控制，不使用 Hutool 的通用日期猜测。

## 导入与持久化流程

新导入路径统一使用 V2：

1. `ExcelArchiveReader` 的普通日期单元格、已关联家庭辅助出生日期和标准年龄公式引用的
   辅助出生日期使用 V2。
2. 声明行提取精确 `时间：` 标签后的完整尾段并交给 V2；不得只接受一个合法前缀，
   因此 `二〇二四.五.三号` 等尾部错字会在声明单元格坐标上明确报错。签名处理不变。
3. 学历、工作经历等重复区块的日期区间使用 V2，仍以完整 `raw_text` 作为无损重建依据。
4. `SnapshotWriter` 为字符串形式的重复区块日期生成投影时使用 V2。
5. 原文和投影在同一个人员快照事务内写入；任一必须校验的日期非法时，整份工作簿失败，
   错误继续包含安全的 Excel 单元格坐标，不产生部分人员数据。

标量业务日期是有类型的模板字段，非空且不合法时继续返回 `TEMPLATE_INVALID`。重复区块
中的自由文本不能可靠解析时不拒绝整份文件，只保留原文并让投影为 `NULL`，延续当前行为。

本次没有表结构变化，不新增 API 字段，也不修改客户端类型。详情、列表、搜索和 Excel
重建仍读取来源原文，例如导入 `二〇二四.五.三` 后，导出的对应单元格仍是
`二〇二四.五.三`。

## 历史数据迁移

新增 MySQL 与 KingbaseES 各自的 Flyway V11 Java 入口，共用
`StructuredSourceValueBackfillV2`：

- 扫描 V9 已存在的全部日期原文列；
- 使用 V2 重新计算对应的 `*_year`、`*_month`、`*_day`；
- 只更新数字投影列，不修改日期原文、年龄原文、`raw_text`、排序、快照关系或审计数据；
- 无法明确解释的原文把相应投影保持或更新为 `NULL`；
- 年龄规则没有变化，但 V11 不需要重写 `age_value`，避免无意义写入；
- 使用固定批量大小和参数化 SQL，不把业务原文写入迁移日志。

V11 对所有日期投影执行确定性重算，而不是只补 `NULL`。这样可以保证当前数据库无论是否
曾由应用写入过投影，最终都与冻结的 V2 规则一致。迁移不新增表或约束，失败时由 Flyway
和数据库事务阻止半完成版本。

## 兼容性与失败处理

- 已经能由 V1 识别的日期，其 V2 结果必须完全相同。
- `SourceValueParserV1.parseDate("二〇二四.五.三")` 必须继续失败，以证明 V10 语义没有
  被回改；同一输入由 V2 成功解析。
- 非法日历日期、错误单位位置、缺少组件、额外文字和模糊表达不因本次扩展而被接受。
- 新格式只影响可确定的数字投影；鉴权、重复判断、覆盖/跳过、审计、分页、照片和文件
  归档流程不变。
- 本次不承诺真实 KingbaseES 运行验证；没有真实实例时只做共享实现和静态迁移契约验证，
  并明确保留该验证边界。

## 测试与验收

实现按测试驱动顺序进行：

1. V2 单元测试先覆盖上表所有格式、V1 回归、三种精度、全角符号、混合分隔符、闰年、
   非法月日、错误后缀和区间歧义。
2. Excel 读取测试使用真实 `.xlsx` 单元格验证 `二〇二四.五.三`，并覆盖家庭辅助日期、
   声明日期完整尾段校验和日期区间；同时断言全角标点、内部空格等原文没有变化。
3. `SnapshotWriter` 测试核对原文与 V2 数字投影一起传入 Mapper。
4. 真实 MySQL 迁移测试先迁到 V10，写入只有 V2 能解释的历史原文，再执行 V11，核对
   投影补齐且所有原文逐字不变。
5. KingbaseES 静态契约测试核对 V11 位于生产 Flyway 路径并调用同一份 V2 回填实现。
6. 完整流程测试核对导入后的数据库投影、详情 API 原文和重建 Excel 原文。
7. 最后用已创建的模拟工作簿通过本地前后端实际导入一次，确认原先的
   `H5 日期格式不正确` 消失，并检查新档案及导出文件。

完成标准是 `./mvnw verify` 通过、真实 MySQL V11 迁移通过、模拟工作簿导入和导出通过，
且 V1/V10 文件内容没有被修改。

## 非目标

- 不新增日期或年龄筛选、排序、统计接口。
- 不把数字投影返回客户端。
- 不改写用户日期格式，不推断缺失的月或日。
- 不接受近似年龄、相对日期或任意自然语言日期。
- 不修改 V1/V10，不重写既有 Flyway 迁移。
- 不修改用户提供的空白模板或此前生成的模拟工作簿。
