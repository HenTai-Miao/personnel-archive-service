# 默认管理员账号凭据轮换设计

**日期：** 2026-08-14

**范围：** `personnel-archive-service` 的 MySQL Flyway 迁移、迁移测试、离线部署契约与配套文档

**目标：** 在不改写任何已发布迁移、不保存明文密码、不影响业务数据的前提下，把固定默认管理员收口到登录账号 `hr_dept` 和已离线验证的 BCrypt cost 12 密码哈希。

## 背景与现状

默认管理员由 MySQL Flyway V8 创建。V8 已经提交并可能在开发库和生产库执行，因此它的内容和校验和都属于不可变历史。当前工作区直接修改了 V8 及部分测试；这种做法只会影响全新数据库，而且会使执行过原始 V8 的数据库在启动时触发 Flyway 校验失败。

桌面客户端不包含固定管理员账号，登录表单把用户输入交给后端认证接口，因此本次不修改桌面客户端、REST API 或客户端类型。`AdminBootstrap` 仍只是“数据库没有任何用户”时的兼容路径，不能承担标准 V8 数据库的凭据轮换。

后端工作区另有一份包含固定生产数据库和安全参数的本地 `application-prod.yml` 修改。它不属于本次账号轮换，必须保持未暂存状态，不能进入提交、构建输出说明或推送内容。

## 设计决策

采用新的 MySQL Flyway V15 迁移，恢复并冻结原始 V8。V15 只修改默认管理员的认证与授权状态，不新增管理接口，不接触人员档案、导入历史、审计业务数据或生产配置。

V15 支持以下两种合法起始状态：

1. 数据库仍保留 V8 创建的旧规范化账号；
2. 运维人员已按照内网操作文档手工把同一用户改为目标规范化账号。

两种情况下都复用现有 `sys_user.id`，从而保留该用户作为历史业务记录操作人的外键关系。迁移统一写入目标 `username`、`normalized_username`、显示名称和已离线验证的 BCrypt cost 12 哈希，同时启用账号、清零失败登录次数、解除锁定，并更新时间戳。

迁移不创建第二个管理员，也不根据显示名称猜测用户。若旧账号和目标账号同时存在，单条账号更新会因租户内规范化账号唯一约束而失败；若二者都不存在，最终的非空用户角色写入会失败。两种异常状态都必须阻止 V15 被标记为成功，避免静默修改错误用户。

## 授权与会话处理

完成账号字段更新后，V15 先确保目标用户具有默认租户的 `ADMIN` 角色关联，再删除该用户所有非 `ADMIN` 角色关联。这样无论迁移前是否被误加 `VIEWER` 或 `ARCHIVE_EDITOR`，迁移后的固定管理员都只有一个 `ADMIN` 关联；如果用户或 `ADMIN` 角色不存在，确保关联的步骤会先失败，不会提前清空其他角色。

密码变更后，V15 撤销该用户所有尚未撤销的持久化会话，写入固定、无敏感信息的内部撤销原因。服务升级重启后内存中的访问令牌自然失效，数据库中的刷新令牌也不能继续换取新访问令牌。已经撤销的会话及其原始撤销信息保持不变。

账号、密码、显示名称和角色收口属于一次部署迁移，不额外生成 `sys_operation_log` 业务审计记录；Flyway 历史表是该变更的权威部署证据。

## 迁移顺序与原子边界

V15 使用 MySQL DML 和现有唯一键、非空约束完成状态验证，不引入存储过程、触发器或永久辅助表。核心顺序如下：

1. 在默认租户内用“旧规范化账号或目标规范化账号”定位唯一迁移对象，并以一条更新语句完成账号、哈希、显示名称、启用和解锁状态收口；
2. 撤销该用户所有活动会话；
3. 通过标量子查询幂等写入唯一 `ADMIN` 关联，使“用户不存在”或“默认角色不存在”成为迁移失败，而不是零行成功；
4. 删除该用户所有非 `ADMIN` 角色关联；
5. 由 Flyway 记录 V15 成功状态。

账号更新本身是单条 MySQL 语句，因此“旧账号与目标账号同时存在”时唯一键冲突不会留下半更新账号。账号收口不得使用 upsert 吞掉冲突；角色关联可以依赖现有唯一键做幂等写入。所有语句必须可在迁移失败后安全排查，并且不得删除任何 `sys_user` 行。

## 测试策略

测试遵循先红后绿，并覆盖静态契约与真实 MySQL 迁移：

- `DefaultAdminMigrationContractTest` 同时锁定原始 V8 不变和新增 V15 的安全契约。测试只检查提交的 BCrypt 哈希格式、cost、迁移结构和目标状态，不在源码中保存或输出明文密码。
- 真实 MySQL 测试从 V14 的标准旧账号状态迁移到 V15，验证用户主键保持不变、旧登录名消失、目标登录名存在、哈希和显示名称正确、账号启用解锁、失败次数归零、活动会话被撤销、既有非 ADMIN 角色被清除且最终只有一个 `ADMIN`。
- 真实 MySQL 测试模拟运维已手工改为目标账号的 V14 数据库，再执行 V15，验证迁移仍成功并把哈希、锁定状态、角色与会话确定性收口。
- 真实 MySQL 测试覆盖异常的双账号状态，验证 V15 失败且不会把两个用户静默合并。
- 全量迁移测试验证空库从 V1 运行到 V15 后的最终默认管理员状态和当前 Flyway 版本。
- 分阶段验证 V13/V14 的测试仍在 V15 之前查询 V8 旧账号，防止测试夹具错误依赖尚未执行的 V15。

最低完成验证为 `./mvnw verify`。真实 MySQL Testcontainers 测试只有在 Docker 可用且实际执行时才能作为迁移通过证据；若被跳过，交付说明必须明确标注。

## 离线部署与文档同步

离线 UOS 构建器和契约测试从 Flyway `V1–V14` 更新为 `V1–V15`，并检查可执行 JAR 包含 V15 SQL。安装和数据库授权文档同步说明服务会运行 V1–V15，验证步骤要求 `flyway_schema_history` 的最大成功版本为 15。

后端 `AGENTS.md`、`README.md` 以及跨项目 `../AGENTS.md`、`../CODE_GUIDE.md` 同步更新：V8 继续描述为历史初始管理员种子，V15 描述为固定管理员账号、哈希、启用/解锁、唯一 ADMIN 角色和会话撤销的轮换迁移。所有文档只记录目标账号和安全行为，不记录明文密码。

项目根目录不是 Git 仓库，因此跨项目文档可以在本地同步，但不能纳入后端仓库提交。后端仓库内的迁移、测试、部署文件、`AGENTS.md`、`README.md`、设计和实施计划必须作为本次可推送变更一起维护。

## Git 与敏感信息边界

本次只操作后端仓库当前分支 `chore/prod-mysql-only`，最终推送到其跟踪的 `origin/chore/prod-mysql-only`。提交前使用显式路径暂存并检查暂存区，确保以下内容不进入提交：

- 本地修改的 `application-prod.yml`；
- `.codex/` 及其他无关未跟踪目录；
- 桌面客户端已有的未推送提交；
- 默认管理员明文密码、数据库密码、令牌 pepper、身份 HMAC/AES 值或生成的生产 JAR。

提交信息只描述“默认管理员凭据轮换”，不包含账号密码或其他凭据值。

## 完成标准

本次变更只有在以下条件全部满足时才完成：

- 原始 V8 与当前提交版本逐字一致，V15 是唯一新增的凭据轮换迁移；
- 标准旧账号、已手工改名账号和异常双账号三条迁移路径都有可核验证据；
- 最终用户保留原主键，处于启用、未锁定状态，且只有 `ADMIN` 角色；
- 所有活动刷新会话被撤销，已有撤销记录不被重写；
- 桌面端和 REST API 无不必要变更；
- V1–V15 离线部署契约、项目说明和代码指南同步；
- `./mvnw verify` 成功，且明确报告 Testcontainers 是否实际运行；
- 暂存区与最终提交不包含本地生产配置、明文密码或无关文件；
- 相关提交成功推送到当前跟踪的内部远程分支。
