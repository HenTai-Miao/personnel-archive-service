# MySQL 与 KingbaseES 双数据库适配设计

## 目标

人员档案数据服务同时支持两条明确的运行路径：

- `local` 及默认开发环境继续使用现有 MySQL，不改变本地数据库、Docker 容器或数据卷。
- `prod` 使用 KingbaseES V9 的 MySQL 兼容模式，应用 JDBC 驱动固定为用户指定的 `cn.com.kingbase:kingbase8:9.0.1`。

本次适配只建立生产空库所需的最终 V7 表结构，不搬迁任何现有 MySQL 数据，不在本机连接或启动 KingbaseES，也不引入 MyBatis-Plus。

## 方案选择

采用“现有 MyBatis + 可移植运行时 SQL + 分数据库 Flyway 迁移”的方案。

不选择仅依赖 KingbaseES MySQL 兼容层的方案，因为当前 MySQL 迁移包含 InnoDB、字符集、排序规则、`AFTER` 和索引定义等实现细节；即使运行时 SQL大多兼容，直接复用整套 DDL 仍会把失败推迟到生产启动阶段。

不迁移到 MyBatis-Plus。MyBatis-Plus 对 KingbaseES 的支持主要位于分页方言和通用 CRUD 扩展，不能转换项目已有的 Flyway DDL、`LAST_INSERT_ID()`、`DATE_ADD()`、`FIELD()` 或字符串转义语义。现有 Mapper 已经完整表达业务查询，替换持久化框架只会扩大回归面。

## 依赖与连接

保留以下 MySQL 路径依赖：

- `com.mysql:mysql-connector-j`
- `org.flywaydb:flyway-mysql`

新增以下生产路径依赖：

- `cn.com.kingbase:kingbase8:9.0.1`，供应用数据源使用，驱动类为 `com.kingbase8.Driver`。
- `org.flywaydb:flyway-database-postgresql` 与 PostgreSQL JDBC 运行时驱动，仅供 Flyway 连接 KingbaseES 使用。

KingbaseES 官方 Flyway 指南使用 PostgreSQL JDBC 协议执行迁移。这样可以继续使用 Spring Boot 4.0.7 管理的 Flyway 11.14.1，避免引入只针对 Flyway 10.22 编译的第三方 Kingbase DatabaseType SPI 适配器。

生产应用数据源默认值为：

```text
jdbc:kingbase8://10.141.29.96:54321/personnel_archive
```

生产 Flyway 数据源默认值为：

```text
jdbc:postgresql://10.141.29.96:54321/personnel_archive
```

两者使用同一个数据库账号。完整连接串、用户名和密码分别由 `PA_DB_URL`、`PA_FLYWAY_DB_URL`、`PA_DB_USERNAME`、`PA_DB_PASSWORD` 覆盖；仓库不保存生产密码。数据库实例、`personnel_archive` 数据库和应用账号必须先由 DBA 创建，Flyway 只管理该数据库内的业务表、索引、约束和种子角色。

## Profile 边界

`application.yml` 保持 MySQL 默认数据源，并继续扫描现有 `classpath:db/migration`。`config/application-local.yml` 不变，仍指向 `127.0.0.1:3306` 的现有 MySQL。

`application-prod.yml` 覆盖以下内容：

- 应用数据源 URL、驱动类、用户名和密码；
- Flyway 独立 URL、用户名、密码和 KingbaseES 迁移位置；
- HTTP 端口继续默认 `18080`。

生产迁移位置固定为 `classpath:db/kingbase`，不会扫描 MySQL 脚本。MySQL 也不会扫描 KingbaseES 脚本。

## KingbaseES 结构基线

KingbaseES 是新的生产空库，因此不逐步重演只服务于既有 MySQL 数据升级的 V1 至 V6。新增 `db/kingbase/V7__kingbase_initial_schema.sql`，一次创建与 MySQL 执行完 V1 至 V7 后等价的最终结构。Flyway 历史版本直接落在 V7，未来 V8 及后续结构变化必须在两个迁移位置各提供同版本脚本。

KingbaseES V7 基线遵循这些映射：

- 主键使用 `BIGINT GENERATED BY DEFAULT AS IDENTITY`，并保留 JDBC generated-keys 行为；
- `DATETIME(6)` 使用 `TIMESTAMP(6)`；
- `BINARY`、`VARBINARY`、`MEDIUMBLOB` 使用 `BYTEA`；
- `TINYINT(1)` 使用带 `0/1` 检查约束的 `SMALLINT`，使共享 SQL 仍使用 `is_deleted = 0/1`；
- `LONGTEXT` 和其他无界文本使用 `TEXT`；
- 所有十二个业务日期字段直接使用 `VARCHAR(64)`，不恢复任何已删除的规范化日期列；
- 家庭成员年龄使用 `TEXT`，只保存导入阶段冻结的源值；
- active employee number 和 identity HMAC 的唯一性使用 KingbaseES 部分唯一索引实现，语义等价于 MySQL 的 nullable generated active-key columns；
- 照片继续保存原始二进制及锚点元数据；
- 所有外键、检查约束、查询索引、默认租户和三个初始角色保持与 MySQL 最终结构等价。

KingbaseES 不依赖 MySQL 的 `ON UPDATE CURRENT_TIMESTAMP`。所有确实会更新的根表和批次表由共享 Mapper SQL 显式写入 `updated_at = CURRENT_TIMESTAMP(6)`；不可变子表只在插入时设置时间。

## 运行时 SQL 可移植化

只修改已确认的数据库专用语句，不重写无关 Mapper：

1. 会话插入改用 `@Options(useGeneratedKeys = true)` 回填主键，删除 `SELECT LAST_INSERT_ID()`。
2. 登录失败锁定截止时间由使用现有 `Clock` 的 Java 服务计算并作为 `Instant` 参数传入，删除 `DATE_ADD(..., INTERVAL 15 MINUTE)`。
3. 教育类型排序把 `FIELD()` 改成标准 `CASE` 表达式。
4. 模糊查询改用 `!` 作为 LIKE escape character；Java 同时转义 `!`、`%`、`_`，SQL 统一使用 `ESCAPE '!'`，避免 MySQL 与 KingbaseES 对反斜线字符串的差异。
5. 所有会改变带 `updated_at` 行的 UPDATE 显式更新时间，消除对 MySQL 自动更新时间戳的依赖。

`LIMIT/OFFSET`、`FOR UPDATE`、`COALESCE`、`CONCAT` 和 `CURRENT_TIMESTAMP(6)` 在目标 MySQL 与 KingbaseES MySQL 兼容模式中继续共用。业务服务、事务边界、DTO、API 和前端协议不变。

## 数据与安全边界

- 不读取、复制或删除用户现有 MySQL 数据。
- 不在仓库写入 KingbaseES 管理员账号、应用密码或任何现有本地密钥。
- 生产密码、令牌 pepper、HMAC key、AES key 和初始管理员凭据继续通过环境变量注入。
- 切换数据库不改变身份信息加密、HMAC 唯一性、软删除历史、审计脱敏、原始日期/年龄文本和照片 BLOB 约束。
- Flyway 连接失败、数据库不存在、账号无权限或迁移失败时，生产服务启动失败；禁止跳过迁移后带着未知结构继续运行。

## 验证范围

遵从用户要求，不连接本机 KingbaseES，也不把任何测试指向用户的现有数据库。

允许并要求执行的验证是：

- 先写配置与 SQL 源码回归测试，验证 `prod` 解析为 KingbaseES、`local` 仍为 MySQL，并验证专用 MySQL 函数已从共享 Mapper 移除；
- 检查 `kingbase8:9.0.1`、Flyway PostgreSQL 模块和 JDBC 驱动进入最终依赖树及可执行 JAR；
- 运行不建立数据库连接的单元测试；
- 执行 Maven 编译和打包；
- 静态检查 KingbaseES V7 基线覆盖最终数据模型、索引和约束。

由于没有可连接的 KingbaseES 实例，本次不能声称生产数据库迁移或端到端业务流已经实际通过。部署后必须由具备 KingbaseES 环境的人员执行一次空库启动、Flyway V7 落库、登录、导入、查询、覆盖、删除和导出验收。
